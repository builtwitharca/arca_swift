### WP-09 -- ArcaLogConsole: build (status: Done)

- AC-09.1 A console line is its text, one of five kinds (log, error, warning, marker and quiet) and the id of the source it came from, which the app gives. The kind is the app's classifier's. The library gives it a start-of-line token, read after one leading RFC 3339 timestamp (a token with only a timestamp's shape is not one): `» ` is a marker, and after any indent of spaces or tabs `error:` and `caused by:` are errors and `warning:` and `remedy:` warnings. Its standard classifier is that token, or log. -- satisfied: yes (computed)
- AC-09.2 A console keeps its lines in one bounded buffer, 5000 by default. The quiet lines and the rest are each kept to the capacity apart, the oldest of each leaving first, so a quiet line never pushes out one that shows. One source's lines can be removed with the rest kept in order, and the buffer cleared. Each batch gives the view one edit, the ranges it removes, last first, and the lines it adds, counting lines rather than newline runs: a line holding a newline leaves as one line, a hidden line takes no text, and a quiet line that leaves while quiet lines show is cut from inside the text. -- satisfied: yes (computed)
- AC-09.3 One line assembler serves a file and a command alike. Bytes are split on 0x0A, each complete line is decoded with bad bytes as U+FFFD, and a fragment is held until its newline arrives, so a character split across two reads stays one character. At a stream's end the fragment held is a line. No line is longer than 256 KiB: a longer run with no newline is given up in pieces, each ending on a character's boundary, so what is held stays bounded. -- satisfied: yes (computed)
- AC-09.4 A file the app names is followed in-process, with no child process: a dispatch source on the open file and one on the nearest folder there is on the way to it, and at each event the open file checked against the one at the path, by identity and size, in one pure decision. Its reads, the replay's included, happen off the main actor, one batch for each event, a failure included, and each read pass reads at most a 256 KiB window, saying how many bytes it passed over. A file or folder that is there but cannot be read is said as an error line, once while it lasts, and again when it comes back. Against real files: an append arrives; a truncated file gives up the fragment it held as a line and is read again from the start, a short append after the truncation included; a renamed file is drained to its end, the fragment it held given up as a line, and then the path's new file is followed, whether it is made a moment later or is there by the event; a log missing at open, or whose folders are missing too, is picked up when it is created; a character split across two writes stays one character; a last line with no newline is held until its newline arrives; and opening replays a bounded backlog of the file's last lines, from the first whole line in its window. -- satisfied: yes (computed)
- AC-09.5 A command the app runs has one pipe for stdout and stderr, read off the main actor as it arrives, one batch for each read, and its stdin held, so the child dies with the app. Its lines, from the command's own source unless the app names one, are framed by `» cmd` and `» exit N · 1.2s`, the exit after the last line, or `» killed by signal N · 1.2s` for a child a signal ended, and a followed command is framed the same way. A second run is refused while one goes. A run always ends: output that a process the child started holds open is cut 2 s after the child ends, with a line saying so. A cancelled run stops its child and says so, and lines dropped because the console fell behind are counted and said. Its launcher and clock are injectable, and it is tested against a stub launcher and against real children. -- satisfied: yes (computed)
