**What happens:** an app that depends on arca_swift 0.1.0 fails to build on Xcode 26 (Swift 6.3.3), the floor's Xcode. Gtools.app's macOS CI job failed in its build step on the runner's Xcode 26.6:

> Conflicting options '-warnings-as-errors' and '-suppress-warnings' (in target 'ArcaCore' from project 'arca_swift')

**Why:** Package.swift:14 gives every target `.treatAllWarnings(as: .error)`. Its comment says SwiftPM drops the setting when an app builds the package as a dependency (SE-0480). Swift 6.4 (Xcode 27) does. Swift 6.3.3 passes it beside the `-suppress-warnings` it gives a dependency, and the compiler refuses the pair. arca_swift's own CI stays green because it builds the package as the root, which is given no `-suppress-warnings`.

**Who it hits:** every adopter on Xcode 26. That's Gtools.app today, menuz once its adoption lands, and Intent.app and Conflab.app in theirs.

**The fix, measured before it is chosen:**
- **The shapes:**
  - the setting only in arca_swift's own builds, eg read from the environment in the manifest, with CI and the local steps setting it;
  - the setting gated on `#if compiler(>=6.4)`;
  - the flag moved to CI's command line, which also reaches Yams and swift-cmark, remote dependencies, and may meet the same refusal there.
- **An adopter job in CI:** a consumer package that depends on arca_swift by URL and revision, built with xcodebuild on the macOS 26 runner. It goes red on 0.1.0's manifest and green on the fix, and it catches this class for all four apps, which the root build cannot.
- **The manifest's comment:** its SE-0480 claim is corrected either way.

**The release:** 0.1.1, with issue 0001. Each adopter's `.upToNextMinor(from: "0.1.0")` allows it.

**Size:** XS for the fix, S with the adopter job.


**Landed:** 7fb5027 on main, on 19 Oct 2026, on local and GitHub.
- **The fix:**
  - The manifest gives its targets `.treatAllWarnings(as: .error)` only when `ARCA_SWIFT_STRICT` is set, read through `Context.environment`.
  - CI's test job sets the variable. README's build and test commands set it on each command, rather than exporting it, so an app's build does not get it.
  - The manifest's comment now names `-warnings-as-errors` and the measured Xcode 26.6 and Swift 6.3.3. It says Swift 6.4 drops the setting for a dependency, as SE-0480 specifies.
- **The adopter job:**
  - A package names arca_swift by `file://` URL and revision, and xcodebuild builds it on macos-26.
  - Xcode 26.6 is named through `DEVELOPER_DIR`. The image's default moves to newer releases, and on Xcode 27 the job would pass on 0.1.0's manifest too.
- **Measured:**
  - **The adopter job** went red on 0.1.0's manifest with this issue's refusal (run 39210789566) and green on the fix (run 39210973743). Both ran on Xcode 26.6 (17F113) and Swift 6.3.3.
  - **The flag on CI's command line,** `-Xswiftc -warnings-as-errors`, passed too. It would also make Yams' and swift-cmark's warnings fatal in arca_swift's own builds, so the environment shape was taken.
  - **`#if compiler(>=6.4)`** was not taken, and not tried: CI builds on Swift 6.3.3, so it would have no strict build at all.
  - **Locally, on Xcode 27.1 and Swift 6.4:**
    - a warning planted in ArcaCore failed the build with `ARCA_SWIFT_STRICT` set and passed without it;
    - swift build, swift test (142 tests in 19 suites) and the format lint passed.
  - **On the landed commit:** run 39214929625 on its branch and run 39215541986 on main were green. Each passed test, with 142 tests in 19 suites, and adopter, with BUILD SUCCEEDED.
- **The release:** 0.1.1, tagged on hv's word, with 0001's outcome.
